AI 功能规划

本文说明平台新增的三个 AI 功能：AI 问诊房间全流程智能体、AI 患者数据总览、上肢报告分析与生成。三者围绕同一个「患者档案 + 训练数据」底座，形成「问诊路由 → 数据总览分析 → 报告输出」的能力链。

功能一：AI 问诊房间全流程智能体

定位：用智能体实现问诊房间内的完整流程——采集病史、量表评估、处方/训练方案、医嘱、邀请医生会诊——由智能体自主判断与推进，替代原先各自独立的固定分支流程。

解决什么问题：问诊房间里的各个环节（病史、量表、处方、医嘱、会诊）现在是各自独立、靠 LLM 逐次判断的固定流程，来回切换慢、上下文割裂，医生要等多次判断。本功能用一个智能体把整个问诊流程连贯地串起来。

功能说明：智能体在问诊房间里自主推进全流程，按需调用工具完成各环节，结合上下文记忆判断下一步该做什么，最终汇总产出病历 / 处方 / 医嘱交医生确认。

优化对比：本功能核心是把「割裂的固定分支」升级为「连贯的智能体全流程」，优化点对比如下：

维度优化前（固定分支流程）优化后（智能体全流程）
流程推进病史 / 量表 / 处方 / 医嘱 / 会诊各环节独立，靠 LLM 逐次判断智能体自主判断当前该做哪一环，连贯推进
上下文各环节上下文割裂，来回切换跨轮记忆 + 结果回填，全程连贯
医生操作反复切换、多次等待判断结果一次接管，智能体自主走完并汇总
信息补全信息不足时硬切流程主动追问补全，不硬切
产出各环节分散的结果汇总病历 / 处方 / 医嘱，交医生一次确认

智能体设计流程

智能体在问诊房间内采用「单 Agent 循环 + 工具调用 + 跨轮记忆」的结构，连贯推进整个问诊流程：

flowchart TD
    A[进入问诊房间] --> B[智能体接管问诊全流程]
    B --> C{判断当前该做哪个环节}
    C -- 采集病史 --> D[病历工具 + 追问补全]
    C -- 量表评估 --> E[量表评估工具]
    C -- 处方/训练方案 --> F[处方工具]
    C -- 医嘱 --> G[医嘱工具]
    C -- 邀请会诊 --> H[在线医生工具]
    D --> I[结果回填上下文与跨轮记忆]
    E --> I
    F --> I
    G --> I
    H --> I
    I --> J{问诊信息是否齐全?}
    J -- 否 --> C
    J -- 是 --> K[汇总产出病历/处方/医嘱]
    K --> L[交医生确认]

分步说明：

  1. 接管全流程：进入问诊房间后，智能体接管整条问诊流程，不再按固定分支逐次切换，而是把「病史 → 量表 → 处方 → 医嘱 → 会诊」作为一个连贯过程来推进。
  2. 自主判断环节：智能体根据上下文与记忆，判断当前该做哪一环节——采集病史、量表评估、处方/训练方案、医嘱、邀请会诊——并调用对应工具执行。
  3. 结果回填记忆：每个环节的结果回填上下文与跨轮记忆，智能体据此决定下一步，无需医生手动指定流程。
  4. 循环推进：不断「判断 → 执行 → 回填」，直到问诊信息齐全；信息不足时主动追问补全，而不是硬切流程。
  5. 汇总与确认：汇总产出病历、处方、医嘱，交医生确认后才生效。

核心价值：把问诊房间内多个割裂的固定环节，升级为一个智能体连贯推进的全流程，减少来回试探，医生接诊更顺畅。

功能二：AI 患者数据总览

定位：一个「患者健康档案 + AI 分析与评估」页——以患者为中心，把各维度数据汇成一份完整健康档案，同时由 AI 对各项指标做综合分析，给出总体结论与康复处方 / 建议，让医生一页看清「现状 + 判断 + 下一步」。

解决什么问题：患者数据散落在多个系统（档案、问诊、下肢/上肢训练、量表），医生要来回翻找才能拼出全貌，更缺乏自动化的解读。本页面把所有数据汇到一处，并给每块数据配 AI 分析，让医生一眼看全、点进去即懂。

功能说明：页面以患者为单位，分两层呈现。上层是患者健康档案——按数据域分区铺开个人信息、问诊记录、下肢报告、上肢数据、量表报告；下层是 AI 综合分析与评估——AI 汇总各域数据，对各项指标（运动功能、认知、依从性、风险因素等）逐项分析，并给出总体结论与康复处方 / 建议。每个分区点进去后仍可看该域的单项 / 对比分析：报告类分区（如下肢报告）先展示该患者的全部报告列表，支持点单份做分析、勾选多份做对比分析。

如何与 AI 串联

每个分区本质上是「该域的数据工具 + 一次定向 AI 分析」。报告类分区（如下肢报告）的点击动作分两步——先拉全部报告列表，再按选择做单份或对比分析：

flowchart LR
    P[点进报告分区] --> L[拉取该域全部报告列表<br/>get_*_patient_history]
    L --> C{勾选报告}
    C -- 选 1 份 --> S[单份分析<br/>get_*_session_analysis]
    C -- 选多份 --> M[多份对比<br/>get_*_longitudinal_analysis]
    S --> A[AI 智能体分析]
    M --> A
    A --> R[摘要/对比 + 趋势 + 风险 + 建议<br/>引用具体记录]
    R --> V[页面展示分析结果]
  • 展示全部报告：拉取该域报告/训练记录列表（如 get_iretour_patient_history / get_irego_patient_history），页面列出全部报告，可翻页、筛选。
  • 单份分析：选 1 份 → 单次分析工具（get_*_session_analysis），给该份的指标、风险、建议。
  • 多份对比：勾选 ≥ 2 份 → 趋势/对比分析工具（get_*_longitudinal_analysis），给指标变化曲线、依从性、方案调整建议。
  • 数据读取复用现有患者三层工具、设备历史/分析工具、量表评估流程，不另建数据通道。
  • AI 分析复用现有智能体：同一套系统提示词 + 工具调用，只是把分析对象限定在该分区对应的数据域。
  • 分析结论引用具体记录（session_ref、量表条目），医生可回溯到原始数据。
  • 分区可扩展：新增数据域（如新设备、新量表）时，加一个工具 + 一个分区即可。
  • 综合评估：页面顶部的「AI 综合分析与评估」由 AI 汇总各分区数据后生成——先对各分区指标逐项分析，再综合出总体结论与康复处方 / 建议，等价于「患者健康档案 + AI 分析与评估」。

核心价值：把「散落的数据」变成「一份健康档案 + 一份 AI 综合评估」——医生一眼看到患者全貌、当前判断与下一步康复处方，不用来回翻系统。

功能三：上肢报告分析与生成

定位：为上肢康复场景补齐「分析 + 报告」能力——对上肢训练数据做单次 / 趋势分析，并生成报告图片，与现有下肢（IReTour / IReGo）报告能力对齐。

解决什么问题：目前报告分析与生成覆盖下肢设备，上肢训练（如书写 Writing、摘水果 Fruit、描红 VRTracing 等游戏类训练）只有起止时间 / 完成状态的会话日志，没有结构化分析与报告图片，医生和患者看不到上肢训练的量化进展。本功能补上上肢这条线。

数据现状与边界（重要）：

  • 当前上肢训练数据在 devicedetaillog / devicedetaillog_item，Details 只存 {start, end, type, state}（起止时间 + 是否完成），没有精细指标（书写轨迹、准确率、关节活动度 ROM、肌力等）。
  • 因此一期只能做粗粒度分析：训练时长、训练频次、坚持度、完成率、训练类型分布。
  • FMA 上肢评分、ROM、肌力等精细指标需上游设备端补充记录后才能支持，列为二期（数据依赖）。

功能说明（分期）：

  • 一期（基于现有数据）：读取上肢会话日志，输出单次分析与连续趋势——训练时长、频次、完成率、坚持度、类型分布，并生成报告图片。
  • 二期（依赖补数据）：设备端补充精细指标后，增加 FMA / ROM / 肌力等维度的分析与报告。

怎么运作（简要）：

  1. 先查上肢训练历史，拿到可用训练记录（session 日志）。
  2. 用户要求出报告时，用该记录引用调用上肢报告生成能力，得到报告图片地址。
  3. 报告按 [Cweb]（图片）+ [web]（对话记录页）+ [Answer] 协议输出，与现有训练报告格式一致。
  4. 记录引用必须来自工具返回，不能由 LLM 凭空编造。

复用与扩展：整体复用现有下肢报告的「分析 → 生成 → 图片下发」链路与协议，新增上肢设备领域（工具、指标字典、报告模板）即可，不改动智能体主流程。

核心价值：先让上肢康复「有记录、能看出练没练、练多久、坚持得如何」，后续补上精细指标后升级为「有指标、有对比、有报告」。
